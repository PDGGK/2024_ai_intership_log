# 开发环境选择与网络问题排查

> **日期**: 2024-12-08
> **主题**: 虚拟机 vs 本地开发环境的权衡

---

## 今天遇到的问题

今天被网络问题折腾了半天，最后决定放弃虚拟机，改用本地开发环境。

---

## 问题描述

虚拟机里的 Web 服务从外部无法访问：
- SSH 能连上
- ping 不通（但这个可能是 ICMP 被禁了）
- curl 虚拟机内部正常，从 Mac 访问 404

---

## 排查过程

### 1. 检查服务状态

```bash
# 在虚拟机内测试
curl localhost:9001/docs  # 正常

# 检查监听地址
netstat -tulpn | grep 9001
# tcp  0  0  0.0.0.0:9001  0.0.0.0:*  LISTEN
```

服务确实在监听 0.0.0.0，理论上外部应该能访问。

### 2. 检查防火墙

```bash
# 查看防火墙规则
sudo iptables -L

# 检查 ICMP 配置
cat /proc/sys/net/ipv4/icmp_echo_ignore_all
# 返回 1，说明 ICMP 被禁用了
```

防火墙没问题，ICMP 被禁了所以 ping 不通，但这不影响 TCP。

### 3. 检查网络模式

虚拟机用的是 NAT 模式。NAT 模式下，虚拟机的 IP 是私有的，需要端口转发才能从外部访问。

但我配置了端口转发还是不行，怀疑是 VMware 的网络配置有问题。

---

## 最终决定

折腾了两个小时，决定放弃虚拟机，改用本地 Python 虚拟环境。

| 方面 | 虚拟机 | 本地 venv |
|------|--------|-----------|
| 隔离度 | 系统级 | 包级 |
| 配置复杂度 | 高 | 低 |
| 资源占用 | 大 | 小 |
| 网络问题 | 容易出问题 | 无 |
| 生产环境模拟 | 好 | 一般 |

对于日常开发来说，本地 venv 就够了。虚拟机的优势是能模拟生产环境，但配置复杂度太高，得不偿失。

---

## 本地环境配置

```bash
# 创建虚拟环境
python -m venv venv

# 激活
source venv/bin/activate

# 安装依赖
pip install -r requirements.txt

# 启动服务
uvicorn startup:app --reload
```

直接访问 `http://localhost:9001/docs`，一切正常。

---

## 网络模式总结

| 模式 | 特点 | 适用场景 |
|------|------|----------|
| NAT | 虚拟机共享主机 IP，需端口转发 | 开发测试 |
| 桥接 | 虚拟机有独立 IP，直接接入网络 | 生产环境模拟 |
| 仅主机 | 只能和主机通信 | 隔离测试 |

如果必须用虚拟机，建议用桥接模式，配置更简单。

---

## 今日反思

今天最大的教训是：**不要过度工程化**。

一开始想用虚拟机是因为觉得"更专业"、"更接近生产环境"。但实际上，对于当前的开发任务，本地 venv 完全够用。虚拟机带来的隔离优势，在这个场景下根本用不上，反而增加了很多配置成本。

另一个教训是：**知道什么时候止损**。排查网络问题花了两个小时，后来意识到即使解决了，以后可能还会遇到类似问题。不如换个更简单的方案。

## Docker + Conda：为什么要结合使用？

一开始我有个疑问：既然有了Docker，为什么还要在里面用Conda？

后来想明白了，它们解决的问题不一样：

- **Docker**：解决的是系统级别的隔离问题，比如操作系统版本、系统库依赖等
- **Conda**：解决的是Python包的依赖问题，特别是那些需要编译的科学计算包

打个比方：Docker像是搬家公司，负责把整个"房子"（运行环境）搬走；Conda像是厨房管理系统，负责管理"厨房"（Python环境）里的各种工具和食材。

## 核心配置

### Dockerfile

```dockerfile
# 基础镜像选择国内源，下载快很多
FROM registry.cn-hangzhou.aliyuncs.com/library/python:3.8-slim

WORKDIR /app

# 安装系统依赖
RUN apt-get update && \
    apt-get install -y wget git && \
    rm -rf /var/lib/apt/lists/*

# 复制并安装Python依赖
COPY environment.yml .
RUN conda env create -f environment.yml
```

这里有几个经验：
1. 用国内镜像源，不然下载慢到怀疑人生
2. `rm -rf /var/lib/apt/lists/*` 可以减小镜像体积
3. 把不常变的操作放在前面，利用Docker的层缓存

### docker-compose.yml

```yaml
services:
  vl_service:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - .:/app
    environment:
      - PYTHONUNBUFFERED=1
```

### environment.yml

```yaml
name: vl_env
channels:
  - conda-forge
  - defaults
dependencies:
  - python=3.8
  - pip:
    - fastapi
    - uvicorn
    - pillow
```

## 踩过的坑

### 1. 层缓存失效

一开始我把 `COPY . .` 放在安装依赖之前，结果每次改一行代码都要重新安装所有依赖，构建巨慢。

**正确做法**：先复制依赖文件，安装依赖，最后再复制代码。

```dockerfile
# 先复制依赖文件
COPY requirements.txt .
RUN pip install -r requirements.txt

# 最后复制代码
COPY . .
```

### 2. 容器里的文件权限问题

容器里创建的文件，在宿主机上可能没有权限操作。解决方法是在docker-compose里指定用户：

```yaml
user: "${UID}:${GID}"
```

## 环境管理的思考

今天接触下来，对环境管理有了更清晰的认识：

| 层级 | 工具 | 职责 |
|------|------|------|
| 系统层 | Docker | 容器隔离、资源管理、服务编排 |
| 应用层 | Conda/pip | 依赖解析、环境复制、版本管理 |

未来如果项目更复杂，可能还需要引入：
- **Kubernetes**：多容器编排
- **Helm**：Kubernetes的包管理
- **Terraform**：基础设施即代码

## 今日反思

今天花了大半天配置环境，虽然没写什么业务代码，但我觉得这个时间投入是值得的。

以前总觉得配置环境是"脏活累活"，能省就省。但这次发现，好的开发环境能大大提升后续的开发效率。而且Docker配置好之后，新同事入职直接 `docker-compose up` 就能跑起来，不用再花半天配环境。

另外一个体会是：**容器化思维很重要**。以前写代码经常依赖本地环境的一些配置，这些隐式依赖在容器里就跑不起来。现在写代码会更注意把依赖显式声明出来。

## 模型设计

### 基础模型

继承 `BaseJudgement`：

```python
class BaseJudgement(BaseModel):
    is_or_not: bool   # 是否违规
    reason: str       # 判断理由
    reference: str    # 法规依据
```

### 场景特定模型

```python
class DiseaseFunctionCheck(BaseModel):
    has_disease_function: bool      # 是否声称疾病功能
    disease_claims: List[str]       # 具体声称列表
    is_valid: bool                  # 是否合规

class HealthFoodAnalysisResult(BaseModel):
    disease_function_check: DiseaseFunctionCheck
    non_drug_statement: BaseJudgement
    label_and_crowd: BaseJudgement
```

### 响应封装

```python
class HealthFoodAnalysisResponse(BaseResponse):
    data: Optional[HealthFoodAnalysisResult]
```

## 错误处理机制

实现了多层错误处理：

```
1. 文件验证层
   └── 检查文件类型和大小

2. OCR 处理层
   └── 处理文本识别失败

3. JSON 解析层
   └── 处理 LLM 返回的格式错误

4. 业务逻辑层
   └── 处理数据验证失败
```

每一层捕获自己负责的异常，向上抛出统一格式的错误信息。

## LLM 提示词设计

这次提示词设计花了不少时间。关键点：

### 1. 结构化输出要求

```python
HEALTH_FOOD_LLM_PROMPT = """
你是保健食品广告审查助手，请分析以下广告内容。

严格按照以下 JSON 格式输出，不要添加任何其他内容：
{
    "disease_function_check": {
        "has_disease_function": false,
        "disease_claims": [],
        "is_valid": true
    },
    "non_drug_statement": {
        "is_or_not": false,
        "reason": "...",
        "reference": "..."
    },
    ...
}
"""
```

### 2. 注意事项

- 明确要求只输出 JSON，不要解释
- 提供完整的 JSON 示例
- 说明每个字段的含义和类型
- 处理中文编码问题

## Pydantic 验证

用 Pydantic 做数据验证：

```python
class DiseaseFunctionCheck(BaseModel):
    has_disease_function: bool
    disease_claims: List[str] = Field(default_factory=list)
    is_valid: bool

    @validator('disease_claims')
    def validate_claims(cls, v):
        # 过滤空字符串
        return [claim for claim in v if claim.strip()]
```

验证器可以：
- 设置默认值
- 类型转换
- 自定义校验逻辑

## 今日反思

今天的场景比昨天复杂很多，主要体现在数据结构上。三个审查场景，每个都有自己的字段，还要组合成一个总的结果。

设计模型时我走了弯路。一开始想把所有场景放在一个大模型里，字段多得眼花缭乱。后来拆成多个小模型，每个模型职责单一，组合起来反而更清晰。这就是"分而治之"的思想。

另一个收获是：**提示词也是代码，需要认真设计**。LLM 的输出质量很大程度取决于提示词的质量。结构化输出的提示词要非常精确，稍微模糊一点 LLM 就可能返回意外的格式。

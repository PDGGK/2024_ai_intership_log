# 异步编程的陷阱：显存溢出问题

> **日期**: 2024-12-02
> **主题**: Python async/await 机制与资源管理

---

## 今天遇到的问题

PDF 处理服务运行一段时间后显存溢出，GPU 直接挂掉。

看日志发现问题：短时间内触发了大量模型推理请求，显存被瞬间吃满。

---

## 问题分析

代码是这样写的：

```python
async def process_pdf_document(content: bytes, prompt: str):
    for page in pages:
        response = await process_page(page)
```

乍一看没问题——每个 `await` 不是会等待吗？

问题在于对 `async/await` 的误解。`await` 确实会等待当前任务完成，但在等待期间，事件循环可能会切换到其他任务。如果有多个 PDF 同时处理，每个 PDF 都在发送页面请求，就会导致请求堆积。

实际执行顺序可能是：

```
PDF1 第1页 await → 切换到 PDF2 第1页 await → 切换到 PDF1 第2页 await...
```

结果就是多个请求几乎同时发送到模型，显存瞬间吃满。

---

## 解决方案

### 方案一：同步处理

最简单直接——把异步改成同步：

```python
def process_pdf_document(content: bytes, prompt: str):
    for page in pages:
        response = synchronous_process_page(page)
```

同步代码严格按顺序执行，一个页面处理完才处理下一个，不存在并发问题。

### 方案二：限制并发

如果需要保留异步，用信号量控制并发数：

```python
async def process_pdf_document(content: bytes, prompt: str):
    semaphore = asyncio.Semaphore(1)  # 最多同时处理1个
    async with semaphore:
        for page in pages:
            response = await process_page(page)
            await asyncio.sleep(3)  # 给 GPU 喘息的时间
```

### 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 同步处理 | 简单可靠 | 无法利用 I/O 等待时间 |
| 信号量控制 | 保留异步优势 | 复杂度高，需要调参 |

对于 GPU 密集型任务，同步处理反而更稳定。异步的优势在于 I/O 等待（网络、磁盘），但 GPU 推理是 CPU/GPU 密集型的，并发反而会增加资源竞争。

## async/await 的正确理解

今天对异步编程有了更深的理解：

```
async/await 的本质：
- await 只是"让出"当前执行权
- 事件循环决定接下来执行什么
- 多个 async 函数可能"交错"执行
```

异步不等于串行。`await` 不是阻塞等待，而是"暂停当前任务，让其他任务有机会执行"。这在 I/O 密集型场景很有用（等网络时可以处理其他请求），但在资源密集型场景会导致资源争用。

---

## 资源管理要点

1. **监控**：实时监控显存使用率
2. **限流**：控制并发数量
3. **释放**：及时释放不用的资源
4. **降级**：资源紧张时降低处理质量

```python
# 显存监控示例
import torch

def check_gpu_memory():
    allocated = torch.cuda.memory_allocated()
    total = torch.cuda.get_device_properties(0).total_memory
    return allocated / total
```

## 今日反思

今天踩了一个典型的异步编程陷阱。

之前觉得 `async/await` 就是"加个 await 就能异步"，没想过多个异步任务交错执行会带来的问题。这次经验告诉我：**选择编程范式要看具体场景**。异步编程适合 I/O 密集型任务，不适合资源密集型任务。

另一个教训是：**出问题时先看日志**。一开始怀疑是模型问题、显存泄漏等，结果看日志发现是请求时间间隔太短。日志时间线清清楚楚显示了问题所在，只是之前没认真看。

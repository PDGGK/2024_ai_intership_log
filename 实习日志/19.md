## 系统架构

整个系统的核心是 VL 模型 + LLM 模型的组合：

```
用户请求 (图片/PDF)
    ↓
FastAPI 路由
    ↓
VL 模型 (视觉语言模型)
    ├── 图像处理
    └── 文字识别 (OCR)
    ↓
LLM 模型 (大语言模型)
    ├── 文本理解
    └── 结构化分析
    ↓
返回结果 (JSON)
```

VL 负责"看"，把图片转成文字；LLM 负责"理解"，根据文字做分析判断。

```python

    data: Optional[Any]

class ProcessedDocument(BaseModel):

class BaseJudgement(BaseModel):
```

## 场景开发流程

开发一个新场景的标准流程：

1. **定义响应模型**
   - 继承 `BaseJudgement` 或自定义
   - 定义场景特定的字段

2. **编写提示词**
   - VL 提示词：告诉模型识别什么内容
   - LLM 提示词：告诉模型如何分析判断

3. **实现场景处理器**
   ```python
   async def recognize_xxx_api(
       file: UploadFile = File(...),
       batch_size: int = Form(default=1)
   ) -> XXXResponse:
       # 1. VL 识别
       processed_doc = await recognizeImageTextVL(file, prompt, batch_size)
       # 2. LLM 分析
       result = await llm_chat(query)
       # 3. 返回结果
       return XXXResponse(...)
   ```

4. **注册路由**
   ```python
   app.include_router(xxx_router, prefix="/api/xxx")
   ```

5. **测试**
   - 用 Apifox 或 curl 测试 API
   - 检查边界情况

## 性能优化策略

### 批处理

`batch_size` 参数控制一次处理多少页。PDF 有很多页时，设置合适的 batch_size 可以平衡速度和显存占用。

### 图像预处理

在送给 VL 模型前做预处理：
- 调整尺寸（太大的图片会占用更多显存）
- 图像增强（提高 OCR 准确率）

### 异步处理

用 `async/await` 处理 I/O 操作，提高并发能力。但要注意之前踩的坑——GPU 密集型任务不适合高并发。

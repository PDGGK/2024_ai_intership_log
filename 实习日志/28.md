# 验证逻辑冲突问题排查

> **日期**: 2024-12-16
> **主题**: Pydantic validator 与 LLM 输出的冲突处理

---

## 今天遇到的问题

保健食品广告审查的判断结果不对——明明检测出问题了，最终结果却显示"合规"。

---

## 问题排查

### 现象

日志显示 LLM 判断有问题，但 API 返回的 `is_or_not` 是 `True`（合规）。

### 原因

问题出在 Pydantic 的 validator 上。我之前写了一个 validator：

```python
@validator('is_or_not', always=True)
def validate_is_or_not(cls, v, values):
    # 这里的逻辑把 LLM 的判断覆盖了
    if some_condition:
        return True  # 强制改成 True
    return v
```

validator 在模型创建时自动执行，把 LLM 返回的结果覆盖了。

---

## 验证流程梳理

数据流向：

```
LLM 返回结果
    ↓
JSON 解析
    ↓
创建 Pydantic 模型
    ↓
validator 执行（问题在这里）
    ↓
返回给用户
```

validator 的执行时机是在模型实例创建时，每个字段都会经过对应的 validator。如果 validator 里有逻辑错误，就会覆盖原始值。

---

## 解决方案

### 方案一：移除 validator

最简单——删掉有问题的 validator。

### 方案二：修正 validator 逻辑

```python
@validator('is_or_not', always=True)
def validate_is_or_not(cls, v, values):
    # 只在特定条件下修改，否则保持原值
    if must_be_invalid_condition:
        return False  # 强制改成不合规
    return v  # 保持原值
```

### 方案三：分离验证和业务逻辑

validator 只做格式验证，业务逻辑放在外面：

```python
# validator 只验证格式
@validator('is_or_not')
def validate_format(cls, v):
    if not isinstance(v, bool):
        raise ValueError('must be bool')
    return v

# 业务逻辑在外面处理
def process_result(llm_result, logo_check_result):
    result = parse_llm_result(llm_result)
    if not logo_check_result.has_logo:
        result.is_or_not = False
        result.reason = "未检测到蓝帽子标志"
    return result
```

我采用了方案三，更清晰。

## 日志的重要性

排查这个问题全靠日志：

```python
logger.info(f"LLM raw result: {llm_result}")
result_json = extract_and_format_json(llm_result)
logger.info(f"Extracted JSON: {result_json}")
```

看日志才发现 LLM 返回的是正确的，问题出在后面的 validator。

---

## 今日反思

今天踩的坑是 Pydantic validator 的副作用。

validator 很强大，可以在模型创建时自动执行验证和转换。但如果 validator 里写了业务逻辑，就容易出问题——validator 的执行是隐式的，不容易发现。

最佳实践是：**validator 只做格式验证，不做业务判断**。格式验证（类型检查、范围检查）是稳定的，不会随业务变化；业务判断是多变的，放在 validator 里会增加维护成本。

另一个教训是：**日志要打在关键节点**。这次如果没有打印 LLM 的原始结果，很难发现问题出在 validator 而不是 LLM。

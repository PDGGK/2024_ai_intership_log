## 背景

开发过程中经常需要访问外部资源（下载模型、拉镜像），公司网络需要配置代理。今天深入学习了代理技术的原理。

---

## 系统代理

### 工作原理

```
应用程序 → 系统代理服务 (127.0.0.1:7897) → 代理服务器 → 目标服务器
```

应用程序的网络请求会被重定向到本地代理服务，由代理服务转发。

### 配置方式

```bash
# 环境变量
export http_proxy=http://127.0.0.1:7897
export https_proxy=http://127.0.0.1:7897

# 临时使用（只对当前命令生效）
http_proxy=http://127.0.0.1:7897 curl https://example.com
```

### 适用场景

- 浏览器
- 支持代理的命令行工具（curl、wget）
- 包管理器（pip、npm）
- API 调用

## TUN 模式

### 工作原理

TUN 通过创建虚拟网卡，在网络层拦截流量：

```
应用程序
    ↓
操作系统网络栈
    ↓
TUN 虚拟网卡（Clash/Mihomo）
    ↓
代理处理
    ↓
物理网卡
```

### 网络堆栈对比

| 堆栈 | 特点 | 适用场景 |
|------|------|----------|
| System | 使用系统原生协议栈，性能好 | 流媒体、大文件传输 |
| GVisor | 用户空间实现，安全隔离 | 安全敏感应用 |
| Mixed | 动态选择 | 复杂环境 |

### 关键参数

- **MTU**：最大传输单元，一般设置 1400-1500
- **DNS**：可以配置 DoH/DoT 加密 DNS

---

## 系统代理 vs TUN

| 方面 | 系统代理 | TUN 模式 |
|------|----------|----------|
| 工作层级 | 应用层 | 网络层 |
| 覆盖范围 | 支持代理的应用 | 所有网络流量 |
| 配置复杂度 | 低 | 高 |
| 性能 | 一般 | 较好 |

**选择建议**：
- 日常开发用系统代理就够了
- 需要全局代理（如容器、虚拟机）用 TUN

---

## DNS 劫持

代理环境下的 DNS 处理：

```
传统流程：
用户请求 → 本地 DNS → 根服务器 → 权威服务器

代理流程：
用户请求 → 代理拦截 → 加密 DNS (DoH/DoT) → 代理服务器解析
```

好处：
- 防止 DNS 污染
- 请求加密
- 更准确的解析结果

## 开发环境配置

### Python

```bash
# pip
pip install xxx -i https://pypi.tuna.tsinghua.edu.cn/simple

# 或设置代理
export http_proxy=http://127.0.0.1:7897
pip install xxx
```

### Docker

```json
// ~/.docker/config.json
{
  "proxies": {
    "default": {
      "httpProxy": "http://127.0.0.1:7897",
      "httpsProxy": "http://127.0.0.1:7897"
    }
  }
}
```

### Git

```bash
git config --global http.proxy http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897
```

## 常见问题

### 代理不生效

1. 检查代理服务是否运行
2. 检查端口是否正确
3. 检查环境变量是否设置
4. 某些应用不读取系统代理，需要单独配置

### 访问变慢

1. 检查代理服务器延迟
2. 尝试切换节点
3. 调整 MTU 值

## 今日反思

今天没写代码，专门学习网络知识。

之前用代理都是"能用就行"，不理解原理。今天学完才知道，系统代理和 TUN 是完全不同的技术，适用场景也不同。理解原理后，遇到代理问题就知道从哪里排查了。

另一个收获是理解了 DNS 劫持。之前以为是坏事，其实在代理场景下，DNS 劫持是为了保证请求走代理通道，避免 DNS 泄露。

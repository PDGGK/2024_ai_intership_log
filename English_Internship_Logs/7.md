## Platform Compatibility

```dockerfile
# Platform declaration
FROM --platform=linux/arm64 python:3.10
```

The `--platform` flag tells Docker the target architecture. Multi-architecture images handle this automatically, but many images don't support multiple architectures.

## Dependency Layering

```python
# Dependency layering structure
requirements/
    base.txt       # Base dependencies
    production.txt # Production environment
    development.txt # Development environment
```

Practical recommendations:
- Use virtual environments for isolation
- Implement explicit version locking
- Manage dependencies in layers
- Utilize dependency hash verification

---

## Multi-Stage Build with Wheels

```dockerfile
# Build stage
FROM python:3.10 AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip wheel --no-cache-dir --no-deps -r requirements.txt

# Runtime stage
FROM python:3.10-slim
COPY --from=builder /build /wheels
RUN pip install /wheels/*
```

Building wheels in a separate stage reduces final image size and speeds up deployment.

## Today's Reflection

Today I learned that **configuration consistency and reproducibility are more important than development convenience** in Docker environments.

It's tempting to add conveniences that make development easier - mounting local directories, running as root, skipping security checks. But these shortcuts create differences between development and production that cause hard-to-debug issues.

The better approach is to make the development container as similar to production as possible, and use tooling (like hot reload mounts) to maintain development speed without compromising consistency.

Another insight: dependency management in containers should use explicit version locking. The `pip freeze` output might work today, but without version pins, builds become non-reproducible over time.

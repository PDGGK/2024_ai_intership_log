# Rule Structure Optimization: A Case Study in Simplification

> **Date**: 2024-02-01
> **Topic**: Applying YAGNI to data structure design

---

## Background

Today I completed a major refactoring of the rule structure, reducing it from 50+ fields to just 6. This is a case study in simplification.

---

## The Original Bloated Structure

```json
{
  "rule_id": "R123456_01",
  "source": "Article X",
  "description": "...",
  "priority": 1,
  "scene_tags": ["..."],
  "requirements": [{"type": "...", "content": "...", "visual_check_required": true, ...}],
  "prohibitions": ["..."],
  "risk_points": [{"description": "...", "severity": "high"}],
  "tools_required": [{"tool": "...", "purpose": "...", "parameters": {...}}],
  "validation_steps": [{"step": 1, "action": "...", "tool": "...", ...}]
}
```

---

## Analysis Process

```python
def analyze_rule_structure(rules: List[Dict]) -> Dict:
    analysis = {
        "fields_usage": defaultdict(int),
        "tools_usage": defaultdict(int)
    }

    for rule in rules:
        for field in rule.keys():
            analysis["fields_usage"][field] += 1

        if "tools_required" in rule:
            for tool in rule["tools_required"]:
                analysis["tools_usage"][tool["tool"]] += 1

    return dict(analysis)
```

Findings:
- `priority` field: used 0 times
- `risk_points`: used 2% of cases
- `validation_steps`: always had exactly 1 step
- Tool information duplicated in 3 places

## The Simplified Structure

```json
{
  "rule_id": "R123456_01",
  "source": "Article X",
  "description": "Rule description",
  "scene_tags": ["YPGG", "QXGG", "BJGG"],
  "validation": {
    "tool": "image_text_recognition",
    "check": "Check advertisement content"
  }
}
```

---

## Migration Tool

```python
async def migrate_rule_structure(old_rule: Dict) -> Dict:
    return {
        "rule_id": old_rule["rule_id"],
        "source": old_rule["source"],
        "description": old_rule["description"],
        "scene_tags": old_rule["scene_tags"],
        "validation": {
            "tool": _get_primary_tool(old_rule),
            "check": _get_check_description(old_rule)
        }
    }

def _get_primary_tool(old_rule: Dict) -> str:
    if "tools_required" in old_rule and old_rule["tools_required"]:
        return old_rule["tools_required"][0]["tool"]
    return "image_text_recognition"  # Default

def _get_check_description(old_rule: Dict) -> str:
    if "requirements" in old_rule and old_rule["requirements"]:
        return old_rule["requirements"][0]["content"]
    return f"Check {old_rule['description']}"
```

## Lessons Learned

1. **YAGNI is real**: We built for flexibility we never needed
2. **Data-driven decisions**: Usage analysis revealed dead code
3. **LLM reliability**: Simpler structures = more reliable generation
4. **Maintenance burden**: Every field is code that needs testing

---

## The YAGNI Principle Applied

Before asking "what if we need this later?", ask:
1. Do we need it now?
2. Is there evidence we'll need it?
3. How hard would it be to add later?

For most fields, the answers were: no, no, and easy.

---

## Today's Reflection

This refactoring was overdue. We'd been carrying complexity for months, working around it rather than removing it.

The psychological barrier is real - deleting code feels wasteful. But unused code isn't an asset, it's a liability. It needs to be understood, tested, and maintained.

The migration was smooth because we:
1. Analyzed before changing
2. Built a migration tool
3. Tested against real data
4. Deployed gradually

Key insight: **complexity is a choice, and you can choose differently**.

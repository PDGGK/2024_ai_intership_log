# Async Programming Pitfalls: GPU Memory Management

> **Date**: 2024-12-02
> **Topic**: GPU memory overflow from async request accumulation

---

## Background

The PDF processing service was crashing with GPU memory overflow errors. Investigation revealed that async/await was causing unintended request accumulation.

---

## The Problem

Multiple model inference requests were triggering simultaneously, exhausting GPU memory. The logs showed many requests starting within milliseconds of each other.

Root cause: misunderstanding of async behavior in a loop.

```python
async def process_pdf_document(content: bytes, prompt: str):
    for page in pages:
        # await here doesn't block the next iteration from being scheduled
        response = await process_page(page)
        # Multiple pages get queued to the model simultaneously
```

---

## Why This Happens

In Python's asyncio, `await` yields control to the event loop, but **the loop itself continues processing**. When you await inside a loop, the runtime can interleave multiple iterations if the awaited operations are queued to the same executor.

For GPU-bound operations, this means multiple images can be sent to the model "simultaneously" from the event loop's perspective, even though you thought you were processing sequentially.

---

## Solutions

### Option 1: Synchronous Processing

```python
def process_pdf_document(content: bytes, prompt: str):
    for page in pages:
        response = synchronous_process_page(page)
        # Truly sequential - no interleaving possible
```

### Option 2: Controlled Async with Semaphore

```python
async def process_pdf_document(content: bytes, prompt: str):
    semaphore = asyncio.Semaphore(1)
    for page in pages:
        async with semaphore:
            response = await process_page(page)
            await asyncio.sleep(3)  # Force cooldown
```

### Option 3: Batch with Memory Monitoring

```python
async def process_with_memory_check(pages, batch_size=2):
    for batch in chunks(pages, batch_size):
        if gpu_memory_usage() > 0.8:
            torch.cuda.empty_cache()
            await asyncio.sleep(2)
        results = await asyncio.gather(*[process_page(p) for p in batch])
```

---

## Key Insight

Async programming's benefits (concurrency, non-blocking I/O) become liabilities when dealing with **resource-constrained operations** like GPU inference. The event loop eagerly schedules work, but GPU memory can't handle the parallelism.

---

## Today's Reflection

This was a humbling debugging session. I'd assumed `await` in a loop meant "wait for this to finish before continuing." That's true for control flow, but not for resource allocation.

The lesson: **async doesn't mean sequential, even with await**. The event loop is always looking for work to do. For GPU operations, you need explicit concurrency control.

I'm now much more careful about async in resource-intensive code. Sometimes synchronous processing is the right choice - simplicity and predictability have value.

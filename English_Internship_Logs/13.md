# VM Boot Issues and UEFI Configuration

> **Date**: 2024-11-29
> **Topic**: Ubuntu ARM64 boot failures, UEFI debugging, and VM lifecycle management

---

## Background

Today I encountered boot failures when trying to install Ubuntu ARM64 in VMware Fusion. The VM wouldn't boot from the ISO, requiring investigation into UEFI and virtual machine configuration.

---

## Problems Encountered

1. **Boot Failure**: Ubuntu ARM64 ISO wouldn't boot
2. **Architecture Mismatch**: Possible x86 ISO on ARM host
3. **UEFI Configuration**: Boot device not recognized

---

## Root Causes

- **Wrong ISO version**: Downloaded x86_64 instead of ARM64
- **UEFI settings**: Boot order not configured correctly
- **Virtual machine state**: Stale configuration from failed attempts

---

## UEFI Boot Process

Understanding the boot sequence helps diagnose issues:

```plaintext
1. Firmware initialization
2. Boot loader detection (searches for EFI partition)
3. Device path recognition
4. Operating system handoff
```

If step 2 fails, the VM shows "no bootable device." This usually means the ISO isn't attached or the UEFI firmware doesn't recognize it.

---

## Virtual Machine Storage

VMware Fusion virtualizes storage with:

- **NVMe**: Modern high-performance interface (recommended)
- **SATA**: Legacy interface, broader compatibility
- **Virtual CD/DVD**: ISO mounting

For ARM64 VMs, NVMe is the default and works well.

---

## VM Lifecycle Management

Proper shutdown/restart procedures:

```plaintext
Clean shutdown: Guest OS shutdown → VMware stops VM → Resources released
Force stop:     VMware terminates VM → May corrupt disk state
Delete VM:      Removes configuration and virtual disks
```

Always use clean shutdown when possible. Force stops can leave the virtual disk in an inconsistent state.

---

## Troubleshooting Checklist

When a VM won't boot:

1. **Verify ISO architecture** - ARM64 ISO for ARM hosts
2. **Check boot device order** - CD/DVD before hard disk
3. **Confirm ISO is attached** - Virtual CD/DVD connected
4. **Try fresh VM** - Create new VM if configuration is corrupted

---

## Today's Reflection

Boot failures are frustrating because the error messages are often unhelpful. "No bootable device" could mean a dozen things.

Today's lesson: **verify assumptions first**. I assumed the ISO was correct because I downloaded it from Ubuntu's site. But I'd grabbed the x86_64 version by habit. On ARM Macs, this doesn't work without emulation.

The UEFI debugging helped me understand the boot process better. In physical machines, we rarely think about firmware - it just works. But in VMs, firmware emulation is another layer that can fail.
